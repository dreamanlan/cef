以后更新 CEF 版本时，可以继续使用现有脚本重新打补丁，但建议采用下面的固定流程。

## 推荐流程

### 1. 在更新前备份补丁脚本

当前脚本位于：

```text
E:\GitHub\CEF_SRC_BUILD\chromium_git\chromium\src\cef\apply_on_before_resource_response_patch.ps1
```

CEF 更新可能覆盖或清理源码目录，因此建议把脚本额外保存在 CEF 工程之外，例如：

```text
E:\GitHub\CEF_SRC_BUILD\patches\apply_on_before_resource_response_patch.ps1
```

只备份脚本即可，不要手工备份并覆盖旧版生成文件。

### 2. 完成 CEF 源码更新

更新后先确认源码目录完整，尤其是以下工具存在：

```text
cef\tools\translator.py
cef\tools\version_manager.py
```

不要先把旧版本的这些生成文件复制到新版本：

- `include/capi/*`
- `libcef_dll/cpptoc/*`
- `libcef_dll/ctocpp/*`
- `cef_api_versions.json`

这些文件应由新版本自带的官方工具重新生成。

### 3. 将脚本复制到新版本 CEF 根目录

脚本依赖 `$PSScriptRoot` 定位 CEF，所以应放在：

```text
<new_cef_root>\apply_on_before_resource_response_patch.ps1
```

例如：

```text
E:\GitHub\CEF_SRC_BUILD\chromium_git\chromium\src\cef\apply_on_before_resource_response_patch.ps1
```

### 4. 先做 PowerShell 语法检查

```powershell
$script_path = "E:\GitHub\CEF_SRC_BUILD\chromium_git\chromium\src\cef\apply_on_before_resource_response_patch.ps1"
$errors = $null
[System.Management.Automation.Language.Parser]::ParseFile(
    $script_path,
    [ref]$null,
    [ref]$errors
) | Out-Null
$errors
```

没有输出表示解析通过。

### 5. 执行补丁脚本

```powershell
cd E:\GitHub\CEF_SRC_BUILD\chromium_git\chromium\src\cef
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\apply_on_before_resource_response_patch.ps1
```

脚本会自动：

1. 修改公共接口。
2. 修改 `resource_request_handler_wrapper.cc`。
3. 修改 `proxy_url_loader_factory.cc`。
4. 添加 `added=next` 和 `CEF_API_ADDED(CEF_NEXT)`。
5. 运行官方 `translator.py`。
6. 运行官方 `version_manager.py -a --replace-next`。
7. 分配新版本对应的 API 版本号。
8. 更新 API 哈希。
9. 验证生成的 C API 回调存在。
10. 不启动构建。

如果 Python 自动检测失败，可以显式指定：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass `
    -File .\apply_on_before_resource_response_patch.ps1 `
    -PythonExecutable "C:\Python311\python3.exe"
```

## 判断是否成功

正常输出应包含类似内容：

```text
Done translating
All NEXT instances successfully replaced.
hashes checked and match
Patch completed successfully.
Build was not started.
```

API 版本号不一定仍是 `15001`。更新后的 CEF 会根据其当前版本记录分配新的版本号，这是正常现象，不应手工改回 `15001`。

`git grep` 返回代码 `1` 如果同时出现：

```text
All NEXT instances successfully replaced.
Patch completed successfully.
```

通常仅表示没有搜到残留的 `CEF_NEXT`，不代表补丁失败。

## 新版 CEF 结构变化时怎么处理

脚本使用严格锚点，不会模糊修改。新版 CEF 如果改动了相关源码结构，脚本可能报：

```text
Expected exactly one source anchor
```

这是安全中止，表示脚本没有可靠地识别新版代码。此时不要反复执行，也不要把旧版文件直接覆盖到新版中；应重新检查新版实现，再对脚本中的锚点和运行时接入点做最小适配。

此外，如果新版 CEF 官方已经提供等价的“CORS 校验前可写响应头”回调，应优先评估官方实现，避免继续维护重复补丁。

## 建议保留的补丁资产

至少在 CEF 源码目录之外保留：

1. `apply_on_before_resource_response_patch.ps1`
2. 一份简短说明，记录补丁目的、验证项和最后验证过的 CEF 版本
3. 当前三个运行时改动的设计说明

最重要的是：**每次更新都在新版原始源码上运行脚本，让新版官方 translator 和 version_manager 重新生成，不要复制旧生成文件。**

## 按实际差异决定是否同步

`translator.py` 本次还报告写入了：

```text
.gitignore
```

生成器即使内容没变化也可能报告“Writing file”。应比较内容：

- 如果 `.gitignore` 实际有变化，则同步。
- 如果内容或哈希未变化，则不用同步。

## 不需要同步

不要同步 Windows 构建产物或平台配置，例如：

```text
out/
build/
*.obj
*.pdb
*.lib
*.dll
*.exe
```

也不要同步 Windows Python 环境、脚本执行日志或中间缓存。

补丁脚本本身：

```text
apply_on_before_resource_response_patch.ps1
```

不是 macOS/Linux 编译所需文件，可以放在独立补丁目录中备份，不必放进其他平台源码树。若希望将来统一维护，可以同步保存，但不要在已经同步上述修改的源码上再次执行它。

## 关键限制

以下情况不能直接同步：

1. macOS/Linux 的 CEF commit 与 Windows 不同。
2. `cef_api_versions.json` 的原始 `last`、`min` 或版本记录不同。
3. 其他平台已经自行增加过 API 版本。
4. 对应运行时文件在其他平台版本中结构不同。
5. 新版 CEF 已经原生加入同名或等价接口。

这时直接复制可能覆盖新版改动或造成 API ABI 不一致，应针对各自源码版本重新适配补丁。

## 同步后的验证

在 macOS/Linux 编译前至少确认：

```text
include/cef_resource_request_handler.h
```

包含：

```cpp

virtual void OnBeforeResourceResponse(...)
```

并确认：

```text
include/capi/cef_resource_request_handler_capi.h
```

包含：

```c
on_before_resource_response
```

同时确认：

- 没有残留 `CEF_NEXT`
- 没有残留 `added=next`
- `cef_api_versions.json` 的 `last` 为 `15001`
- `cef_api_untracked.json` 与 Windows 保持一致
- C API、CppToC、CToCpp 文件中的版本均为 `15001`

## 推荐做法

最稳妥的是将上述 **10 个确定修改文件** 作为一个完整补丁文件集同步到 macOS/Linux，而不是只复制三个人工修改文件。因为公共头文件、C API、双向包装和 API 哈希共同构成 ABI 闭环，缺少其中任何一部分都可能导致编译或运行时版本不一致。

## 需要注意的限制

### 1. 必须使用 PowerShell 7

不能直接通过 Bash 执行：

```bash
./apply_on_before_resource_response_patch.ps1
```

除非另外添加 shebang 和执行权限。推荐始终明确使用：

```bash
pwsh -File ...
```

### 2. CEF 源码版本必须匹配

如果 Windows、macOS 和 Linux 使用相同 CEF commit，推荐只在一个平台打一次，然后同步完整修改文件。

如果在三个平台分别执行，必须确保执行前：

- CEF commit 相同
- `cef_api_versions.json` 相同
- `cef_api_untracked.json` 相同
- 没有其他平台自行分配过 API 版本

否则可能在不同平台分配不同 API 版本号，造成 ABI 和 API 哈希不一致。

### 3. 文件名大小写必须正确

macOS/Linux 文件系统通常区分大小写。脚本使用的路径是：

```text
include/cef_resource_request_handler.h
libcef/browser/net_service/resource_request_handler_wrapper.cc
libcef/browser/net_service/proxy_url_loader_factory.cc
tools/translator.py
tools/version_manager.py
```

不要更改目录或文件名大小写。

### 4. 新版 CEF 改变源码结构时会安全退出

脚本采用严格锚点。如果新版 CEF 改了相关代码，可能出现：

```text
Expected exactly one source anchor
```

这表示脚本没有可靠识别新版代码，并非权限问题。此时不要反复运行，也不要模糊替换，应先适配脚本锚点。

### 5. 权限与依赖

执行用户必须有权限修改 CEF 源码。CEF 官方 Python 工具如果依赖 Git 状态或其他 Python 模块，也必须满足其原有运行要求。

## 推荐选择

如果三个平台源码完全相同，优先采用：

1. Windows 上执行一次补丁和官方生成。
2. 验证 API 哈希通过。
3. 将完整修改文件同步至 macOS/Linux。
4. macOS/Linux 不再重复运行脚本。

只有在各平台分别维护独立源码树、无法同步修改文件时，才建议分别执行脚本。分别执行后必须比较：

```text
cef_api_versions.json
cef_api_untracked.json
include/capi/cef_resource_request_handler_capi_versions.h
```

确保 API 版本号和哈希完全一致。

------------python3补丁脚本用法------------

可以，Python 3 更适合作为 Windows、macOS、Linux 共用的补丁入口，也无需额外安装 PowerShell 7。

建议将现有 PowerShell 脚本等价迁移为 Python 脚本，保持以下特性：

- 最后验证公共接口和生成 C API
- 支持参数指定 CEF 根目录，而不是必须把脚本复制进源码树
